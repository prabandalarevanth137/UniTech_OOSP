01 / PROJECT OVERVIEW

Make file integrity
visible and testable.

A focused systems exercise: inspect a file’s mode, remove write access, then observe how the kernel handles a write attempt.

A / THE PROBLEM
↗

Writable binaries can be changed.

If a process can write to an executable, its contents may be modified, corrupted, or replaced. This project examines the file-mode layer of that risk.

B / THE OBJECTIVE
◎

Inspect before changing access.

Read metadata, identify execute bits, present the current mode, and make each permission change observable.

C / THE APPROACH
⌘

Use standard POSIX calls.

Combine stat(), chmod(), and file I/O operations in a C workflow with explicit error reporting.

D / EXPECTED OUTCOME
✓

A repeatable permission check.

Demonstrate how clearing write bits affects an ordinary write attempt and how saved permissions can be restored.

PERMISSION MODEL / WHY IT MATTERS

Executable status and write access are separate bits.

Linux stores read, write, and execute permissions for owner, group, and others. An executable is not automatically protected from edits: a class with write permission may modify its contents. Clearing write bits reduces access for those classes while leaving execute bits intact. The kernel evaluates access for the calling process using ownership, credentials, ACLs, and other policy too.

04 / C SYSTEM CALL EXPLORER

Small calls. Explicit outcomes.

Illustrative snippets for a C implementation. Check each return value and preserve the original mode before changing it.

permission_check.cC / POSIX
/* Inspect the file and save its permission bits. */
struct stat info;
if (stat(path, &info) == -1) {
    perror("stat");
    return 1;
}
mode_t original = info.st_mode & 0777;

/* Remove write bits, then test write access. */
if (chmod(path, original & ~0222) == -1)
    perror("chmod");
int fd = open(path, O_WRONLY);
if (fd == -1) {
    int error = errno;
    fprintf(stderr, "open: %s\n",
            strerror(error));
} else {
    write(fd, data, length);
    close(fd);
}
Illustrative only — add headers, validate inputs, and handle every error in a complete program.

What to expect

If the calling process lacks effective write access, a write-only open commonly fails with EACCES. A privileged process or another access-control rule can change that outcome. A successful open does not prove bytes were written; check write() and handle partial writes.

07 / SECURITY LIMITATIONS

Mode bits are one layer.

Removing write bits can reduce ordinary access. It does not guarantee that a file cannot be changed.

01

Ownership & privileges

Only an authorized owner or privileged process can change many file modes. A process with sufficient privilege may still write.

02

ACLs & access context

Access control lists, directory permissions, mount options, capabilities, and security modules can affect effective access.

03

Permission changes

Mode bits can be changed again by an authorized process. A check followed by use can also create race conditions.

04

Restore carefully

Save the original mode and restore it only when appropriate. Handle failures so a temporary change does not leave unexpected state.

!

Interpret results in context. A denied open() is evidence about that process and environment at that moment, not proof of universal immutability.
